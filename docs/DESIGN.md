# Architecture & Design

Technical design of the Dr. Shreyas Orthopedic Clinic website and appointment
system. For day-to-day content edits see [`APP_GUIDE.md`](./APP_GUIDE.md); for
build and release mechanics see [`DEPLOYMENT.md`](./DEPLOYMENT.md).

---

## 1. Goals and constraints

| Goal | Consequence for the design |
| --- | --- |
| Patients must **never** create an account | Booking is anonymous; identity is a verified mobile number, not a user row |
| A slot must never be double-booked | Booking is a single Postgres transaction guarded by an advisory lock |
| Patient data must stay private | Row-Level Security is the enforcement layer, not the UI |
| The clinic runs in India | All date/time decisions resolve in `Asia/Kolkata`, never server-local time |
| Content must be editable without a developer | Everything is in the database, edited at `/settings` |
| Must be cheap and fast worldwide | SSR at the edge on Cloudflare Workers |

## 2. System topology

```
                    ┌────────────────────────────┐
   Visitor ────────▶│  Cloudflare Worker (edge)  │
                    │  drshreyasorthopedic       │
                    ├────────────────────────────┤
                    │ • SSR React (TanStack)     │
                    │ • Static assets (ASSETS)   │
                    │ • Server functions (RPC)   │
                    └───────┬────────────┬───────┘
                            │            │
         publishable key    │            │  service-role key
         (RLS enforced)     │            │  (RLS bypassed)
                            ▼            ▼
                    ┌────────────────────────────┐
                    │   Supabase (Lovable Cloud) │
                    │   Postgres + Auth + Storage│
                    └────────────────────────────┘
                                 ▲
                                 │ Twilio Verify (SMS OTP)
```

There is no separate backend service. Privileged logic runs as **TanStack
server functions** inside the same Worker.

## 3. Technology choices

| Layer | Choice | Why |
| --- | --- | --- |
| Framework | TanStack Start (React 19, Vite) | File-based routing with real SSR and typed server functions in one project |
| Styling | Tailwind CSS v4 + shadcn/ui | Design tokens in `src/styles.css`; rebrand without touching components |
| Data | Supabase Postgres | RLS lets the database own authorization instead of the UI |
| Server logic | `createServerFn` | Privileged code that never ships to the browser |
| Hosting | Cloudflare Workers | SSR at the edge; Nitro `cloudflare-module` preset is built in |
| Patient identity | Twilio Verify | Avoids storing passwords or running our own OTP delivery |
| Validation | Zod | One schema shared by client and server function boundaries |

## 4. Rendering model

Three rendering behaviours coexist:

| Route group | Behaviour | Reason |
| --- | --- | --- |
| Public pages (`/`, `/book`, `/gallery`, …) | Server-rendered | SEO and fast first paint |
| `sitemap[.]xml.ts` | Server route returning XML | Generated from live data |
| `_authenticated/*` | `ssr: false` | Dashboards are private; no SEO value and no reason to render patient data server-side |

Data loading follows one pattern:

1. The route **loader** calls `queryClient.ensureQueryData(...)` on the server.
2. The component reads the same query with `useSuspenseQuery(...)`, hitting a
   warm cache — no loading flash, no double fetch.

> **`/doctor`, `/reception` and `/settings` return HTTP 200 when logged out.**
> This is intentional, not a vulnerability. Because they are `ssr: false`, the
> server returns a ~5 KB empty shell and the auth redirect happens in the
> browser. The route guard is a UX convenience; **RLS is the real boundary**, so
> the shell contains no data.

## 5. Data model

Singleton configuration, content tables, and transactional tables:

```
clinic_settings (id = 1)          ← singleton: name, contact, fees,
                                     slot_duration_minutes, max_per_slot
working_hours   (weekday 0–6)     ← morning/evening open + close
blocked_dates                     ← holidays and closures

treatments      ── is_active, fee, duration_minutes
doctors         ── is_active, sort_order
gallery / testimonials / faqs     ← public content

patients (mobile UNIQUE)
   └── appointments (booking_code UNIQUE)
            └── doctor_notes

user_roles (user_id → auth.users, role app_role)
patient_manage_sessions (token_hash PK)
otp_codes                         ← legacy, superseded by Twilio Verify
```

Key details:

- **`patients.mobile` is `UNIQUE`** and acts as the natural key. Booking upserts
  on it, so a returning patient updates their demographics rather than creating
  a duplicate record.
- **`appointments.booking_code`** is generated by the database:
  `'APT-' || upper(replace(gen_random_uuid()::text, '-', ''))`. It is the
  patient-facing reference and is unguessable.
- **Denormalised snapshots** — `appointments` stores `patient_name`,
  `patient_mobile` and `treatment_name` alongside the foreign keys, so historic
  records still read correctly after a treatment is renamed or deactivated.
- **`status`** is one of `confirmed | checked_in | completed | cancelled |
  no_show`. Only the first three consume slot capacity.
- **`app_role`** is an enum: `('doctor', 'receptionist')`.

## 6. Security model

### Three trust zones

| Zone | Credential | Can do |
| --- | --- | --- |
| Browser | `sb_publishable_…` | Read public content only. RLS filters everything else. |
| Worker (server functions) | `sb_secret_…` / service role | Everything. Never reaches the browser. |
| Staff session | Supabase Auth JWT | Scoped by `user_roles` via RLS |

The publishable key is **public by design** — it ships in the client bundle and
is meaningless without a permissive RLS policy. The service-role key bypasses
RLS entirely and exists only as a Worker secret.

### Role helpers

```sql
has_role(_user_id uuid, _role app_role) RETURNS boolean  -- SECURITY INVOKER, STABLE
is_staff(_user_id uuid)                 RETURNS boolean  -- SECURITY INVOKER, STABLE
```

Both are `REVOKE`d from `anon` and granted to `authenticated` and
`service_role`. They read `user_roles`, which is itself protected by
`users read own roles` (`auth.uid() = user_id`) — so a signed-in user can prove
their own role but cannot enumerate anyone else's.

`user_roles` has **explicit deny policies** for INSERT/UPDATE/DELETE
(`WITH CHECK (false)`). Roles are granted only out-of-band by an administrator;
privilege escalation is impossible through the API.

### Effective permissions

| Table | `anon` | `authenticated` | `service_role` |
| --- | --- | --- | --- |
| `clinic_settings`, `faqs`, `working_hours`, `blocked_dates`, `gallery` | read | read; doctor writes | all |
| `treatments` | read where `is_active` | staff read all | all |
| `testimonials` | read where `is_published` | staff read all | all |
| `doctors` | read where `is_active` | staff manage | all |
| `patients`, `appointments` | **none** | staff read/write | all |
| `doctor_notes` | none | staff read, doctor write | all |
| `otp_codes`, `patient_manage_sessions` | none | none | all |

> Postgrest returns **`200` with `[]`** — not `403` — when RLS filters every
> row. A `200` from `/rest/v1/patients` is therefore *not* evidence of a leak;
> the body must be inspected.

### The booking security boundary

The September 2026 migration (`20260926070000_patient_booking_security.sql`)
removed anonymous write access entirely:

```sql
REVOKE INSERT, UPDATE ON public.appointments FROM anon;
REVOKE INSERT, UPDATE ON public.patients     FROM anon;

REVOKE ALL ON FUNCTION public.book_clinic_appointment(...) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.book_clinic_appointment(...) TO service_role;
```

Before this, the browser inserted appointment rows directly, so anyone could
forge bookings or write arbitrary patient rows. Now the only path is:

```
browser ──▶ bookAppointment() server fn ──▶ service-role client ──▶ RPC
              (Zod validation)                                      (SQL validation)
```

Both RPCs are **`SECURITY INVOKER`**, which matters: they execute with the
caller's privileges. Granting `anon` EXECUTE would therefore *still* fail,
because `anon` no longer has INSERT on the underlying tables. There is no
configuration shortcut around the service-role key — this is deliberate.

## 7. Booking flow

```
/book wizard  ─▶ bookAppointment (server fn)  ─▶ book_clinic_appointment (SQL)
  client-side        Zod schema:                   1  validate mobile + name
  step validation    mobile /^[6-9]\d{9}$/         2  reject past date/time (IST)
                     payment_method: "clinic"      3  advisory lock on (date,time)
                                                   4  load clinic settings
                                                   5  treatment must be active
                                                   6  clinic open, date not blocked
                                                   7  time aligns to the slot grid
                                                   8  capacity check
                                                   9  upsert patient by mobile
                                                  10  insert appointment
                                                  ─▶ returns booking_code
                                                     ─▶ redirect /booking/$code
```

Validation is deliberately repeated at all three layers. The client layer is
UX, the Zod layer rejects malformed input at the trust boundary, and **the SQL
layer is authoritative** — it is the only one that cannot be bypassed.

### Concurrency

Two patients competing for the last slot are serialised by a transaction-scoped
advisory lock keyed on the slot itself:

```sql
PERFORM pg_advisory_xact_lock(hashtextextended(p_date::text || '/' || p_time::text, 0));
```

The lock is taken **before** the capacity count, so the check-then-insert
sequence is atomic. It releases automatically at commit or rollback. Without
it, two concurrent transactions could both read `count = 0` and both insert.
The loser receives `"This slot was just taken. Please pick another"`.

### Slot generation

`getAvailableSlots` builds the grid from `working_hours` (morning and evening
sessions) in `clinic_settings.slot_duration_minutes` steps, then subtracts:

- dates in `blocked_dates`, and days where `is_open = false`
- slots already at `max_per_slot` capacity (counting only `confirmed`,
  `checked_in`, `completed`)
- slots in the past, compared against **clinic-local time**

The server function and the database independently enforce the same rules, so a
crafted request cannot book a slot the UI would not offer.

### Time zone handling

All clinic-time decisions go through `src/lib/clinic-time.ts`, which formats via
`Intl.DateTimeFormat` with `timeZone: "Asia/Kolkata"` and returns
`{ date, minutes }`. The SQL layer independently uses
`now() AT TIME ZONE 'Asia/Kolkata'`.

This matters because the Worker runs in UTC. Using server-local time would make
the clinic appear closed — or accept bookings in the past — for 5½ hours each
day.

Weekday lookup uses `new Date(`${date}T00:00:00Z`).getUTCDay()`. Pairing a
`Z`-suffixed string with `getUTCDay()` is correct and drift-free; using
`getDay()` here would be a bug.

## 8. Patient identity (OTP)

Patients never get an account. To manage a booking they prove ownership of a
mobile number:

```
/manage → sendOtp(mobile)   → Twilio Verify sends a 6-digit SMS to +91…
        → verifyOtp(code)   → Twilio "approved"
                            → 32 random bytes → 64-char hex token
                            → store SHA-256(token) in patient_manage_sessions
                            → set httpOnly cookie with the RAW token (30 min)
```

Design points:

- **Only the hash is stored.** A database leak cannot be replayed as a session.
- The cookie is `httpOnly`, `sameSite: lax`, and `secure` in production.
- `requirePatientMobile()` re-validates format, hash match, and `expires_at` on
  every privileged call, then returns the verified mobile.
- Authorization is scoped by that mobile: `cancel_patient_appointment(id,
  mobile)` matches on `patient_mobile`, so one patient cannot touch another's
  booking even with a valid session.
- Cancellation is refused within one hour of the appointment, enforced in SQL:
  `(appointment_date + appointment_time) > (now() AT TIME ZONE 'Asia/Kolkata') + interval '1 hour'`.
- **Fails closed**: with Twilio env vars absent the endpoint throws
  `"SMS verification is not configured"` rather than degrading.
- `VITE_PATIENT_MANAGE_ENABLED` gates the whole `/manage` UI and defaults to
  `false`, so the feature stays dark until Twilio is configured and tested.

## 9. Staff access

Email + password via Supabase Auth at `/auth`. Authorization is *not* derived
from being logged in — it comes from a row in `user_roles`:

- **doctor** — full access, including clinic settings and content
- **receptionist** — appointments, check-in, payments; no settings

Adding staff is a two-step, deliberately manual process: the user signs up, then
an administrator inserts the `user_roles` row.

## 10. SEO

- Per-route `head()` supplies title, description, canonical and Open Graph tags;
  `src/lib/seo.ts` holds `SITE_URL` and shared helpers.
- `/sitemap.xml` is generated at request time from live routes and content.
- `public/robots.txt` points at the sitemap.
- Public pages are server-rendered so crawlers receive complete markup.

`SITE_URL`, the sitemap `BASE_URL` and `robots.txt` must be updated together
when the domain changes.

## 11. Notable decisions

**Server functions instead of Supabase Edge Functions.** Booking logic lives in
the same deployment as the UI, so it ships atomically with the frontend and
shares Zod schemas and types. The cost is that the Worker needs the service-role
key.

**Business rules in SQL, not application code.** Slot validation, capacity and
the cancellation window live in the RPC. Any client — the website, a future
mobile app, a staff tool — inherits identical rules, and they cannot be
bypassed by calling the API directly.

**`SECURITY INVOKER` over `SECURITY DEFINER`.** The booking RPCs deliberately do
*not* run with elevated privileges. Combined with service-role-only EXECUTE,
this means a mistaken `GRANT` to `anon` would still not expose write access —
two independent controls must fail, not one.

**Denormalised snapshots on `appointments`.** Historic records stay accurate
when treatments change. Accepted trade-off: the copies can drift from the source
row, which is the desired behaviour here.

**Pay-at-clinic only.** The schema supports `payment_method = 'online'` and
`paid_online`, but the booking validator hard-codes the literal `"clinic"`.
Online payment is schema-ready and intentionally not enabled.

## 12. Known limitations

- **Booking requires `SUPABASE_SERVICE_ROLE_KEY`.** Without it the site serves
  every page but `/book` fails. There is no fallback by design.
- **No automated tests.** There is no test script. Slot generation, the IST
  boundary and the cancellation window are the highest-value candidates.
- **`otp_codes` is legacy.** Superseded by Twilio Verify; retained by migration
  note until the SMS flow is verified in production.
- **Lint is noisy.** ~1100 Prettier violations inherited from generated code, so
  CI gates on typecheck rather than lint. `pnpm format` clears them.
- **Gallery storage reads are staff-only** since
  `20260926090000_gallery_storage_read_staff.sql`. Public gallery images are
  served from bundled assets, not the Storage bucket.
- **Assets referenced via `*.asset.json`** resolve to Lovable's private CDN and
  404 anywhere else. Import images directly so Vite bundles them.
